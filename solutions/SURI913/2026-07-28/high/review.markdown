#### 시간복잡도 `O(N)`

> 
>    Checkpoint : 이진트리, 서브트리의 크기 계산
>   
>   트리를 직접 구현 하는 건 비효율적. => 기존 이진트리랑 다르게 부모위치를 알고 있어야 함.
>   가능하다면 **배열로 표현**하는게 효율이 좋다. 
>   


**자식의노드값을 인덱스로 써서 부모**값을 찾아냄.
배열에는 아래와 같이 값이 들어감.

| parent index ⇒ 자식 노드값 | value ⇒ 부모 노드 값 |
| --- | --- |
| [1] |  |
| [2] | 1 |
| [3] | 1 |
| [4] | 2 |
| [5] | 3 |
| … | … |


**부모노드 값을 인덱스로 써서 자식**들을 찾아냄. => **2차원 배열**이어야 함.[0]은 왼쪽, [1]은 오른쪽으로 봄. -> 트리 전위 순회라고 보면 됨. children은 벡터로 구현했을 때 보기 편한 듯.

| [Parent index][left] | value ⇒ 자식 노드 값 | [Parent index][right] | value |
| --- | --- | --- | --- |
| [1][0] | 2 | [1][1] | 3 |
| [2][0] | 4 | [2][1] |  |
| [3][0] | 5 | [3][1] | 6 |
| [4][0] | 7 | [4][1] |  |
| [5][0] | 8 | [5][1] | 9 |
| … | … | … | … |


가장 가까운 부모를 찾아야하는 게 목적이니까 이런식으로 배열 접근이 찾기가 더 용이함. 트리구조를 직접 만들어서 구현해도 무방하나, 배열 저장 방식만 이해가 잘 된다면 이쪽 방향이 알고리즘풀이에선 더 효율적

```text
          1
        /   \
       2     3
      /     / \
     4     5   6
    /     / \
   7     8   9
```

여기서  8,6의 공통 부모를 찾으려면 8을 인덱스로 써서 바로 위의 부모를 찾아서 기억해야함 <br/> => visited[V+1]을 씀.

```text
  current = parent[current]
```
노드 한쪽의 부모를 모두 체크하고 다른 쪽도 같은 부모를 만날 때까지 돌다보면 공통부모를 찾을 수 있다.

공통 부모를 기준으로 서브트리의 크기를 계산하는 건 DFS로 구현
반복문으로 구현해도 가능하지만 그러면 이중포문으로 돌려야해서 시간복잡도가 올라갈?까?
